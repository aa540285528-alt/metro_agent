# alembic 设计说明

## 职责与边界

`alembic` 负责数据库 schema 迁移，是 `conversation_history` 和 `observability` 等持久化模块的结构演进入口。它描述"数据库表结构如何变化"，不承载业务查询、Agent 编排、评测执行或页面展示逻辑。

数据库模型定义在业务模块中维护（如 `conversation_history/models.py`、`observability/models.py`），迁移脚本在本目录中记录版本化变更。运行时代码不应直接修改迁移文件来改变行为。

---

## 目录结构总览

```
alembic/
├── alembic.ini                      # Alembic 全局配置（项目根目录）
├── env.py                           # 迁移运行环境，加载模型元数据
├── script.py.mako                   # 迁移脚本生成模板（Mako 模板引擎）
├── versions/
│   ├── 20260717_01_create_conversation_history.py   # V1：对话历史表
│   ├── 20260720_02_create_agent_observability.py     # V2：Agent 可观测性表
│   └── 20260720_03_add_evaluation_entities.py        # V3：评测与分块建库表
└── 设计说明.md                       # 本文档
```

## 主要组件详解

### 1. `alembic.ini` — 全局配置文件

位于项目根目录，是 Alembic 的入口配置。关键配置项：

| 配置项 | 值 | 说明 |
|---|---|---|
| `script_location` | `alembic` | 迁移脚本所在目录 |
| `prepend_sys_path` | `.` | 将项目根目录加入 `sys.path`，使 `env.py` 能导入业务模块 |
| `sqlalchemy.url` | *(空)* | 故意留空，实际连接串由 `env.py` 中的 `get_url()` 从环境变量 `DATABASE_URL` 动态读取 |

日志配置定义了三个 logger：
- **root**：WARN 级别，输出到 stderr
- **sqlalchemy.engine**：WARN 级别，避免打印所有 SQL
- **alembic**：INFO 级别，迁移执行时可看到版本号输出

将 `sqlalchemy.url` 留空并用环境变量覆盖的设计，确保了数据库凭据不会随代码提交到版本控制中。

### 2. `env.py` — 迁移运行环境

这是每次执行 `alembic upgrade/downgrade` 时的入口脚本，核心职责：

**模型元数据装载（第 9–10、18 行）：**
```python
from conversation_history.models import Base
import observability.models
target_metadata = Base.metadata
```
- 导入 `conversation_history.models.Base`（SQLAlchemy `declarative_base`），并将其 `metadata` 设为 Alembic 的 `target_metadata`
- `import observability.models` 是副作用导入——该模块在 import 时会将表定义注册到同一个 `Base.metadata` 上
- 这意味着 `target_metadata` 聚合了所有业务模块的表结构，Alembic 可据此检测模型与数据库实际 schema 的差异（用于 `--autogenerate`）

**数据库连接获取（第 21–22 行）：**
```python
def get_url() -> str:
    return os.environ.get("DATABASE_URL", config.get_main_option("sqlalchemy.url"))
```
- 优先读取环境变量 `DATABASE_URL`，fallback 到 `alembic.ini` 中的配置
- 单一函数封装，便于测试时 mock

**两种运行模式：**

| 模式 | 函数 | 触发条件 | 行为 |
|---|---|---|---|
| **Online** | `run_migrations_online()` | 默认 | 通过 SQLAlchemy engine 连接真实数据库，在事务中执行 DDL |
| **Offline** | `run_migrations_offline()` | `--sql` 标志 | 不连数据库，生成 SQL 脚本输出到 stdout（用于审查或手动执行） |

Online 模式的关键细节：
- 使用 `poolclass=pool.NullPool` 禁用连接池——迁移是单次短连接，不需要池化
- 在 `connection` 上下文内执行迁移，确保整个迁移在一个数据库事务中完成
- `NullPool` 避免了迁移完成后连接残留的问题

### 3. `script.py.mako` — 迁移脚本模板

Mako 模板，`alembic revision --autogenerate` 命令生成新迁移文件时使用。模板中的变量 `${...}` 由 Alembic 在生成时填充：

| 模板变量 | 含义 | 示例值 |
|---|---|---|
| `${message}` | 迁移描述（docstring） | `"Create conversation history tables."` |
| `${up_revision}` | 当前版本 revision ID | `"20260717_01"` |
| `${down_revision}` | 依赖的上一个版本 ID | `"20260717_01"` |
| `${create_date}` | 生成时间戳 | `"2026-07-17 00:00:00"` |
| `${upgrades}` | 自动生成的 upgrade 代码 | 一系列 `op.create_table(...)` 等 |
| `${downgrades}` | 自动生成的 downgrade 代码 | 一系列 `op.drop_table(...)` 等 |

模板为每个迁移文件定义了标准结构：导入区 → revision 元变量 → `upgrade()` 函数 → `downgrade()` 函数。

### 4. `versions/` — 迁移版本链

当前共 3 个迁移版本，形成线性依赖链：

```
(null)
  └── 20260717_01 (create_conversation_history)
          └── 20260720_02 (create_agent_observability)
                  └── 20260720_03 (add_evaluation_entities)
```

每个迁移文件包含一组 `revision` / `down_revision` / `branch_labels` / `depends_on` 元变量，以及 `upgrade()` 和 `downgrade()` 两个核心函数。

#### V1: `20260717_01` — 对话历史

**依赖：** `None`（基线版本，直接作用在空数据库上）

**创建表：**

|---|---|---|---|
| `id` | `String(128)` | PK, NOT NULL | 对话唯一标识 |
| `owner_id` | `String(128)` | NOT NULL | 所属用户 ID，支持多租户 |

| `updated_at` | `DateTime(tz=True)` | NOT NULL, `server_default=now()` | 最后更新时间 |

##### `conversation_messages` — 对话消息表

| 列 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | `Integer` | PK, AUTOINCREMENT | 消息自增 ID |
| `conversation_id` | `String(128)` | FK → `conversations.id`, ON DELETE CASCADE | 所属对话 |

## 数据流与生命周期

```
业务模型变更
    │
    ▼
┌──────────────────────────────────────┐
│ 1. 修改 SQLAlchemy 模型定义           │  ← conversation_history/models.py
│    (添加/修改/删除 Column)            │    observability/models.py
└──────────────────────────────────────┘
    │
    ▼
┌──────────────────────────────────────┐
│ 2. 生成迁移脚本                       │
│    $ alembic revision --autogenerate │  ← 对比 metadata 与数据库实际 schema
│       -m "描述信息"                    │
└──────────────────────────────────────┘
    │
    ▼
┌──────────────────────────────────────┐
│ 3. 审查生成的迁移脚本                  │  ← 自动生成可能不精确（重命名检测、默认值等）
│    手动调整 upgrade/downgrade         │    需要人工确认
└──────────────────────────────────────┘
    │
    ▼
┌──────────────────────────────────────┐
│ 4. 执行迁移                           │
│    $ alembic upgrade head            │  ← 在事务中顺序执行所有未应用的版本
│    (或 alembic upgrade +2 等)        │
└──────────────────────────────────────┘
    │
    ▼
┌──────────────────────────────────────┐
│ 5. 验证                               │
│    $ alembic current                 │  ← 查看当前版本
│    $ alembic history                 │  ← 查看迁移历史链
└──────────────────────────────────────┘
```

**版本链管理：** 每当 `alembic revision` 创建新版本时，会自动将 `down_revision` 设为当前 head 版本，形成严格线性链。部署时 `alembic upgrade head` 会遍历这条链，只执行尚未应用的版本。

**关键原则：**
- 开发阶段先修改业务模型，再生成或手写 Alembic migration
- 线上启动前，数据库必须处于代码期望的 migration 版本
- 若 schema 未升级，历史记录、trace、span、token usage 或评测监控相关查询可能失败

## 依赖与配置

### 外部依赖

| 依赖 | 用途 |
|---|---|
| `alembic` | 迁移框架核心 |
| `SQLAlchemy` | ORM，提供 `MetaData`、engine 和 DDL 构造 |
| `conversation_history.models` | 对话模块的模型定义，提供 `Base` 声明基类 |
| `observability.models` | 可观测性模块的模型定义，import 时注册表到 `Base.metadata` |
| 数据库驱动（如 `psycopg2` / `asyncpg`） | 由 `DATABASE_URL` 的 scheme 决定，不直接 import |

### 配置流

```
alembic.ini (script_location, 日志)
    │
    ▼
env.py 被 Alembic 加载
    │
    ├── import conversation_history.models.Base
    ├── import observability.models (副作用：注册表)
    │
    ├── get_url() → os.environ["DATABASE_URL"] ?? alembic.ini sqlalchemy.url
    │
    └── target_metadata = Base.metadata
```

数据库连接字符串不应写进迁移脚本，应从环境变量或项目配置读取。`env.py` 应只做迁移上下文准备，不应导入会触发模型调用、网络请求、索引加载或 Web 服务启动的模块。

## 持久化与产物

本目录本身保存迁移脚本（版本记录），不保存业务数据。真正持久化的数据位于配置指向的数据库中，包括：

- 对话历史（`conversations`、`conversation_messages`）
- Agent trace（`agent_traces`）
- 执行 span（`agent_spans`）
- LLM 用量（`llm_usages`）
- 工具调用（`tool_calls`）
- RAG 检索（`rag_retrievals`）
- 评测运行与结果（`eval_runs`、`eval_case_results`）
- 分块建库（`chunk_builds`、`chunk_items`）

**迁移版本是数据库结构的审计记录，不能随意删除或重写已经被应用的版本。** 每个版本文件中的 `revision` ID 和 `down_revision` 构成不可变的 DAG（当前为线性链），一旦版本被部署到任何环境，其 ID 和内容就不应再修改，否则会导致版本链断裂。

数据库中有一张 Alembic 自动维护的 `alembic_version` 表，只存一行当前版本的 revision ID。`upgrade head` 会比对这张表和 `versions/` 中的版本链，确定需要执行哪些迁移。

## 异常处理与测试策略

### 异常处理

- 迁移失败时应**停止启动或部署流程**，而不是让运行时以部分 schema 继续工作
- 每个 migration 在 `upgrade()` 中通过 `op.` 执行 DDL；Alembic 在 online 模式下将这些操作包裹在数据库事务中——任一步骤失败则整个版本回滚
- 新增迁移要关注**向前升级（upgrade）和必要时的回滚策略（downgrade）**：
  - V1、V2、V3 均提供了完整的 `downgrade()` 实现
  - downgrade 严格按 upgrade 的逆序执行（先删子表/索引，再删父表）
  - 带 `ON DELETE CASCADE` 的外键在删父表时自动清理子表数据
- **幂等性注意事项：** `op.create_table` 等方法默认不具备幂等性——重复执行会因表已存在而失败。Alembic 通过 `alembic_version` 表保证每个版本只执行一次，但手动操作数据库后需谨慎

### 测试策略

| 测试类型 | 方法 | 验证目标 |
|---|---|---|
| **迁移执行** | 在临时数据库（如 SQLite in-memory）上运行 `alembic upgrade head` | 迁移脚本语法正确、无依赖缺失 |
| **Schema 一致性** | 对比 `Base.metadata` 与实际数据库 `inspector` 结果 | 模型定义与迁移产物一致，无遗漏字段/约束 |
| **downgrade 往返** | `upgrade head` → `downgrade base` → `upgrade head` | 升降级来回无残留数据或约束冲突 |
| **索引覆盖** | 抓取业务模块中的查询语句，EXPLAIN 分析 | 迁移创建的索引覆盖了核心查询路径 |
| **数据完整性** | 插入边界值数据后执行迁移 | 新增 NOT NULL 列有默认值、类型变更不丢失精度 |

## 维护建议

1. **新增持久化模型后同步补 migration**：不要在模型文件中定义了 Column 却忘记生成迁移
2. **迁移脚本中写清楚默认值、nullable 策略和索引意图**：V1 中 `server_default=sa.false()` 和 `server_default=sa.func.now()` 是好的示例——默认值放在数据库层而非仅 ORM 层
3. **不要把数据清洗、评测计算或 trace 汇总逻辑塞进 Alembic migration**：复杂数据修复应单独写一次性脚本，与 schema 变更分开管理。Migration 应只做 DDL（CREATE/ALTER/DROP），不做 DML（大规模 INSERT/UPDATE/DELETE）
4. **每次生成迁移后人工审查**：`--autogenerate` 无法检测列重命名（会生成 drop + create）、无法推断合理的默认值、可能遗漏必要的索引
5. **版本 ID 采用日期前缀命名**：当前命名约定 `YYYYMMDD_NN_description`，既保证排序一致性，又具有可读性
6. **downgrade 必须完整可逆**：每个 `upgrade()` 的每一行操作，在 `downgrade()` 中都应有对应的逆操作，且顺序完全相反
7. **大表变更需评估锁表风险**：`ALTER TABLE ... ADD COLUMN` 在某些数据库（MySQL、特定版本的 PostgreSQL）上会持有排他锁；对于大表应先评估，必要时采用"新表 + 数据迁移 + 重命名"的分步策略
8. **`alembic_version` 表不应手动修改**：手动篡改版本号会导致 Alembic 跳过或重复执行迁移，造成难以排查的 schema 不一致

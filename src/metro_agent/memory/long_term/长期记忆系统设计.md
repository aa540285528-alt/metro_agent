# 长期记忆系统设计文档

## 1. 概述

长期记忆系统（`long_memory_system`）是 Metro Agent 多智能体协作框架的跨会话持久化记忆子系统。与短期记忆系统（单次会话内的上下文管理）不同，长期记忆负责**跨会话复用用户信息**，包括身份、偏好、计划、目标等，数据持久化存储在 ChromaDB 向量数据库中。

### 1.1 核心目标

| 目标 | 说明 |
|------|------|
| **跨会话持久化** | 用户信息在会话结束后不丢失，下次对话自动召回 |
| **自动提取** | 从自然对话中智能识别值得长期保存的信息，无需用户手动管理 |
| **冲突感知** | 检测新旧记忆之间的重复、互补、替换、冲突关系，避免数据冗余和矛盾 |
| **用户确认机制** | 对敏感信息或冲突记忆，要求用户确认后才写入，保障用户知情权 |
| **用户隔离** | 按 `user_id` 严格隔离，检索只返回当前用户的活跃记忆 |
| **价值评分** | 基于类别、来源、使用频率的动态评分体系，驱动记忆优先级排序 |

### 1.2 与短期记忆的对比

| 维度 | 短期记忆 (`short_memory_system`) | 长期记忆 (`long_memory_system`) |
|------|----------------------------------|--------------------------------|
| **生命周期** | 单次会话内，会话结束即丢弃 | 跨会话持久化，直到被主动删除或过期 |
| **存储介质** | LangGraph state (内存 + Redis checkpoint) | ChromaDB 向量数据库 (磁盘持久化) |
| **内容类型** | 对话消息历史 | 用户身份、偏好、计划、目标、需求等结构化记忆 |
| **检索方式** | 按轮次截断 + token 预算控制 | 向量相似度检索 + 类别过滤 |
| **压缩策略** | 旧对话 → ≤100字摘要替代原文 | 重复记忆去重 / 冲突记忆替换 / 过期自动归档 |
| **触发时机** | 每轮对话的固定工作流节点 | 每轮对话结束时自动执行 |

### 1.3 模块全景

```
long_memory_system/
├── models.py                  # 数据模型：MemoryRecord、MemoryCandidate、MemoryCategory 枚举
├── curator.py                 # 记忆策展器：LangMem + Ollama 从对话提取候选记忆
├── policy.py                  # 策略引擎：关键词分流 + 冲突关系裁决
├── conflict_detector.py       # 冲突检测器：向量相似度初筛 + LLM 细粒度判定
├── chroma_store.py            # ChromaDB 向量存储：upsert / search / list_active / delete
├── memory_service.py          # 记忆服务编排层：串联策展→策略→冲突→存储的完整流水线
├── memory_nodes.py            # LangGraph 节点：封装 MemoryService 为工作流节点
├── memory_recall_nodes.py     # 记忆召回节点：按类别查询并返回格式化的记忆内容
└── memory_intent.py           # 意图识别：判断用户是否在查询记忆 + 识别记忆类别
```

## 3. 阶段一：意图路由 — 区分记忆查询与普通对话

**模块**：`memory_intent.py`

每轮对话开始前，系统首先判断用户意图：是在**查询**已有记忆，还是在**提供**新信息。

### 3.1 三级判断逻辑

```
用户输入
    │
    ▼
┌──────────────────────────────────────┐
│ 第一级：直接召回模式                  │
│ "你记得我"、"查看我的记忆"、"我是谁"  │
│ 等 7 种固定模式 → 命中直接返回 True   │
└────────────────┬─────────────────────┘
                 │ 未命中
                 ▼
┌──────────────────────────────────────┐
│ 第二级：个人记忆查询                  │
│ 条件 (三者同时满足)：                 │
│  a. 包含记忆类别关键词（偏好/计划等）  │
│  b. 包含"我"字                       │
│  c. 包含疑问标记（吗/哪些/?...）      │
│ 例："你有什么偏好？" → True           │
└────────────────┬─────────────────────┘
                 │ 未命中
                 ▼
┌──────────────────────────────────────┐
│ 第三级：助手记忆查询                  │
│ 条件 (三者同时满足)：                 │
│  a. 包含"记忆"一词                   │
│  b. 包含疑问标记                      │
│  c. 包含助手记忆动词（你记得/你存了..）│
│ 例："你还存了什么记忆？" → True       │
└────────────────┬─────────────────────┘
                 │ 未命中
                 ▼
          普通对话 → 走写入流程
```

### 3.2 记忆类别检测

通过关键词子串匹配识别用户查询的记忆类别：

| 类别 | 触发关键词 |
|------|-----------|
| `plan` | 计划、安排、打算 |
| `goal` | 目标、目的 |
| `preference` | 偏好、喜欢、习惯 |
| `identity` | 身份、个人信息 |
| `requirement` | 要求、需求 |

## 4. 流程 A：记忆写入（持久化流水线）

**编排层**：`memory_service.py` → `MemoryService.process_turn()`

每轮普通对话结束后，系统执行完整的 **7 步流水线**，从对话中提取信息并决定是否写入长期记忆。

### 4.1 步骤 0：记忆查询短路

```
is_memory_query(user_text) → True
    → 跳过整个写入流水线，返回 MemoryTurnResult(ignored=["记忆查询不写入长期记忆"])
```

记忆查询（如"你记得我的偏好吗？"）只触发召回流程，不触发写入流程。

### 4.2 步骤 1：规则修改检测

```
is_rule_change_request(user_text)
    匹配逻辑：同时包含动作词（写入/修改/删除...）+ 目标词（规则/规则文件...）
    → 命中 → rule_change_requested=True，跳出流水线
```

用户修改系统规则是特殊操作，不应被当作普通记忆处理。

### 4.3 步骤 2：策展提取 — Curator

**模块**：`curator.py`

使用 **LangMem** 框架 + **Ollama Qwen2.5 7B** 从对话中自动提取结构化记忆候选项。

```
user_text + assistant_text
    │
    ▼
┌──────────────────────────────────────┐
│ LangMem create_memory_manager        │
│   schemas=[MemoryCandidate]          │  ← 强制输出符合 schema
│   instructions=MEMORY_INSTRUCTIONS   │  ← 系统提示词定义提取规则
│   enable_inserts=True                │
│   enable_updates=False               │  ← 不在此层更新/删除
│   enable_deletes=False               │
└────────────────┬─────────────────────┘
                 │
                 ▼
           list[MemoryCandidate]
           每条候选项包含:
           {
             category:    "preference" | "plan" | "identity" | ...
             content:     "用户偏好简短回答"
             sensitivity: "normal" | "sensitive"
             evidence:    "我喜欢简短回答"  ← 用户原话
             target_date: 可选目标日期
             valid_until: 可选有效期
           }
```

**MemoryCandidate 数据模型**：

```python
class MemoryCandidate(BaseModel):
    category: MemoryCategory       # 记忆类别
    content: str                   # 记忆正文
    sensitivity: MemorySensitivity # 敏感度 (normal/sensitive)
    evidence: str                  # 提取依据的用户原话
    target_date: date | None       # 目标日期 (计划/目标类)
    valid_until: date | None       # 有效期截止日期
```

### 4.4 步骤 3：初评（无 relation）— Policy 关键词分流

**模块**：`policy.py` → `evaluate_memory(relation=None)`

在调用昂贵的向量检索和 LLM 冲突检测之前，先用**关键词匹配**做快速分流：

```
输入: candidate (无 relation)
    │
    ▼
┌──────────────────────────────────────────────────┐
│ 规则 1: 规则修改请求？                             │
│ → route_rule_change                              │
├──────────────────────────────────────────────────┤
│ 规则 2: 临时状态？                                │
│ 时间词（当前/实时/现在/此刻）                      │
│ + 状态词（告警/设备状态/链路状态...）               │
│ → ignore ("当前告警或临时状态不进入长期记忆")        │
├──────────────────────────────────────────────────┤
│ 规则 3: 敏感信息？                                │
│ candidate.sensitivity="sensitive"                │
│ 或包含敏感关键词（身份证/密码/手机号/银行卡号...）  │
│ → ask_confirmation ("记忆包含敏感信息")            │
├──────────────────────────────────────────────────┤
│ 全部未命中 → auto_save (进入下一步)               │
└──────────────────────────────────────────────────┘
```

**关键词词典**：

| 词典 | 示例词 |
|------|--------|
| 临时时间词 | 当前、实时、现在、此刻 |
| 临时状态词 | 告警、设备状态、链路状态、接口状态、在线状态 |
| 敏感信息词 | 身份证、手机号、密码、口令、token、密钥、银行卡号、家庭住址 |
| 规则动作词 | 写入、添加、修改、更新、删除 |
| 规则目标词 | 规则、规则文件、Metro_Agent_Rules.md |

### 4.5 步骤 4：向量检索已有记忆

初评通过（`auto_save`）的候选项，进入向量检索阶段：

```
candidate.content
    │
    ▼
┌──────────────────────────────────────┐
│ ChromaMemoryStore.search()           │
│   user_id = 当前用户                  │
│   query = candidate.content          │
│   limit = MEMORY_SEARCH_LIMIT        │
│   where: {user_id, status="active"}  │
└────────────────┬─────────────────────┘
                 │
                 ▼
      list[MemorySearchResult]
      (按用户隔离 + 向量相似度排序)
                 │
                 ▼
      过滤：仅保留同 category 的记忆
      （不同类别不构成冲突）
                 │
                 ▼
      取相似度最高的一条作为比对对象
```

### 4.6 步骤 5：冲突检测 — 两级判定

**模块**：`conflict_detector.py`

已有同类记忆时，判断新旧记忆之间的关系类型。

#### 五类关系类型

| 关系 | 含义 | 后续处理 |
|------|------|----------|
| `duplicate` | 语义基本相同 | 忽略，不重复写入 |
| `complement` | 内容不同但可同时成立 | 双写保留 |
| `replace` | 用户明确替换旧要求 | 覆盖旧记忆 |
| `conflict` | 两者矛盾但用户未明确取舍 | 需用户确认 |
| `unrelated` | 无直接关系 | 各自独立存储 |

#### 两级检测流程

```
existing(已有记忆) vs candidate(新候选)
    │
    ▼
┌────────────────────────────────────────┐
│ 第一级：向量相似度快速初筛              │
│ calculate_similarity(existing, candidate)│
│   - 批量嵌入（同一 embedding 模型）     │
│   - 余弦相似度计算                      │
│   - ≥ MEMORY_DUPLICATE_THRESHOLD        │
│     → 直接返回 duplicate                │
│     → 跳过 LLM 调用（省延迟、省成本）   │
└────────────────┬───────────────────────┘
                 │ 相似度不足阈值
                 ▼
┌────────────────────────────────────────┐
│ 第二级：LLM 细粒度语义判定              │
│ DeepSeek LLM + ConflictDecision schema │
│ SystemMessage: CONFLICT_PROMPT         │
│ HumanMessage:                          │
│   用户原话 + 已有记忆 + 候选记忆 + 相似度│
│        ↓                               │
│ ConflictDecision:                      │
│   relation: duplicate/complement/      │
│             replace/conflict/unrelated │
│   has_conflict: bool                   │
│   requires_confirmation: bool          │
│   reason: str                          │
└────────────────┬───────────────────────┘
                 │
                 ▼
        修正: replace/conflict →
          has_conflict = True
          requires_confirmation = True
```

**关键设计**：第一级向量相似度充当"快速通道"——高相似度直接判重复，避免 LLM 调用，大幅降低延迟和成本。只有边界情况才提交 LLM 做细粒度判定。

### 4.7 步骤 6：复评（带 relation）— Policy 结合冲突结果

初评（步骤 3）仅靠关键词判断，不知道新旧记忆的语义关系。此处在拿到 `relation` 后做**第二次策略裁决**：

```
evaluate_memory(relation="replace" | "conflict" | ...)
    │
    ▼
┌──────────────────────────────────────────────────┐
│ 规则 4: relation == "duplicate"                  │
│ → ignore ("已有语义重复的长期记忆")               │
├──────────────────────────────────────────────────┤
│ 规则 5: relation in {"replace", "conflict"}      │
│ → ask_confirmation ("新记忆可能替换或冲突已有记忆")│
├──────────────────────────────────────────────────┤
│ 规则 6: 默认（complement/unrelated/无已有记忆）   │
│ → auto_save ("普通且无冲突的长期记忆")            │
└──────────────────────────────────────────────────┘
```

### 4.8 步骤 7：执行最终裁决

```
最终裁决
    │
    ├── auto_save ──────────────────────────────────┐
    │   create_memory_record()                       │
    │   ├── source="explicit" (category=explicit)    │
    │   └── source="automatic" (其他类别)            │
    │   store.upsert(record) → ChromaDB 向量化写入   │
    │   result.saved.append(record)                  │
    │                                                │
    ├── ask_confirmation ────────────────────────────┤
    │   PendingMemory(                               │
    │     candidate,                                 │
    │     existing_memory_id,  ← 冲突的已有记忆ID    │
    │     existing_content,    ← 冲突的已有记忆内容  │
    │     relation,            ← 关系类型            │
    │     reason               ← 待确认原因          │
    │   )                                           │
    │   result.pending.append(...)                   │
    │                                                │
    └── ignore ─────────────────────────────────────┘
        result.ignored.append(reason)
```

**执行结果汇总** (`MemoryTurnResult`)：

```python
class MemoryTurnResult(BaseModel):
    saved: list[MemoryRecord]               # 成功写入的记忆
    pending: list[PendingMemory]            # 等待用户确认
    ignored: list[str]                      # 被忽略的原因
    rule_change_requested: bool             # 是否检测到规则修改
```

## 6. 数据模型详解

### 6.1 MemoryRecord（完整记忆记录）

```python
class MemoryRecord(BaseModel):
    # ---- 核心标识 ----
    memory_id: str              # UUID 唯一标识
    user_id: str                # 所属用户

    # ---- 内容与分类 ----
    category: MemoryCategory    # identity/preference/plan/goal/requirement/explicit
    content: str                # 记忆正文
    source: MemorySource        # explicit(用户显式) / automatic(系统自动提取)
    sensitivity: MemorySensitivity  # normal / sensitive
    evidence: str               # 提取依据的用户原话

    # ---- 时间戳 (UTC) ----
    created_at: datetime
    updated_at: datetime
    last_accessed_at: datetime | None

    # ---- 统计信息 ----
    access_count: int           # 被检索到的总次数
    retrieved_count: int        # 被放入上下文的次数
    used_count: int             # 实际被用于生成回答的次数

    # ---- 价值评分 (0.0 ~ 1.0) ----
    initial_value: float        # 初始价值 = importance + source_bonus
    current_value: float        # 当前价值（随时间/使用情况动态调整）
    importance: float           # 基础重要性（来自类别）
    utility: float              # 效用性评分（根据使用反馈动态调整）

    # ---- 状态与版本 ----
    pinned: bool                # 是否置顶（置顶=1.0满分）
    status: MemoryStatus        # active / superseded / archived / deleted
    version: int                # 版本号（每次更新递增）

    # ---- 时间约束 ----
    target_date: date | None    # 目标日期（计划/目标类）
    valid_until: date | None    # 有效期（过期自动归档）

    # ---- 版本链 ----
    previous_id: str | None     # 上一版本 ID（被 replace 时建立链）
```

### 6.2 记忆类别与初始重要性

```
重要性值:  explicit > identity > requirement = goal > plan > preference
           0.90      0.85       0.80         0.80   0.70    0.60
```

| 类别 | 标识 | 初始重要性 | 说明 |
|------|------|:---:|------|
| 显式记忆 | `explicit` | 0.90 | 用户明确要求"记住这个"，最高优先级 |
| 身份信息 | `identity` | 0.85 | 姓名、角色、组织 |
| 长期需求 | `requirement` | 0.80 | 明确提出的跨会话需求 |
| 长期目标 | `goal` | 0.80 | 用户的长期目标 |
| 用户计划 | `plan` | 0.70 | 正在进行的任务（时效性强，略低） |
| 用户偏好 | `preference` | 0.60 | 喜欢/不喜欢的风格（可塑性大，最低） |

### 6.3 来源加成

```
显式记忆 (explicit): importance + 0.05
自动提取 (automatic): + 0.00
初始价值上限: 1.0
```

例如：用户明确说"记住，我喜欢简短回答" → 偏好类 (0.60) + 来源加成 (0.05) = 初始价值 0.65

### 6.4 记忆状态生命周期

```
         create_memory_record()
                 │
                 ▼
           ┌─────────┐
           │ active  │  ← 正常使用中，参与检索
           └────┬────┘
                │
        ┌───────┼────────┐
        ▼       ▼        ▼
   superseded archived deleted
   (被新版本  (过期归档) (逻辑删除,
    覆盖)               不参与检索)
        │
        ▼
   previous_id 链
   指向旧版本
```

- **active** → 正常参与检索
- **superseded** → 被新版本覆盖（通过 `previous_id` 追溯历史）
- **archived** → `valid_until` 过期，不参与检索但保留备查
- **deleted** → 逻辑删除，不参与检索

## 7. ChromaDB 向量存储

**模块**：`chroma_store.py`

### 7.1 技术栈

| 组件 | 说明 |
|------|------|
| 向量数据库 | ChromaDB PersistentClient（磁盘持久化） |
| 嵌入模型 | HuggingFace Embeddings（通过 config 注入） |
| 索引类型 | HNSW，余弦空间 (cosine) |
| 数据隔离 | 按 `user_id` + `status="active"` 过滤 |

### 7.2 核心操作

| 操作 | 方法 | 说明 |
|------|------|------|
| 写入/更新 | `upsert(record)` | 文本 → 嵌入向量 → 写入 ChromaDB，id 相同则覆盖 |
| 向量检索 | `search(user_id, query, limit)` | query 嵌入 → 向量相似度查询 → 返回 MemorySearchResult 列表 |
| 列表查询 | `list_active(user_id, category?)` | where 条件过滤，按 updated_at 降序，返回 dict 列表 |
| 删除 | `delete(memory_id)` | 按 ID 删除单条记忆 |

### 7.3 相似度计算

```
ChromaDB 返回 cosine distance (0=完全相同, 2=完全相反)
    ↓
score = max(0.0, 1.0 - distance)
    ↓
相似度分数 (0.0 ~ 1.0，越高越相似)
```

### 7.4 search vs list_active

| | `search()` | `list_active()` |
|------|------------|-----------------|
| **触发场景** | 冲突检测（找到与候选最相似的已有记忆） | 记忆召回（用户查询某类别的所有记忆） |
| **查询方式** | 向量相似度（语义搜索） | where 条件过滤（精确匹配） |
| **返回内容** | 带相似度分数的前 N 条 | 该类别下所有活跃记忆 |
| **排序** | 按相似度降序 | 按 updated_at 降序 |

## 8. 工厂函数与价值计算

**模块**：`models.py` → `create_memory_record()`

```
create_memory_record(
    user_id, category, content, source,
    sensitivity, evidence, **可选参数

    │

自动填充:

├── created_at = now(UTC)
├── updated_at = now(UTC)
```

### 8.1 敏感信息保护

```python
if sensitivity == "sensitive" and not confirmed:
    raise ValueError("敏感记忆必须经过用户确认")
```

敏感记忆的 `create_memory_record` 需要传入 `confirmed=True`，这在上层 `memory_service.py` 中由 `ask_confirmation` 流程控制，确保用户知情同意后才写入。这是**两层防御**的第二层——即使 Policy 漏判了敏感信息，工厂函数也会阻止写入。

## 10. 两阶段策略裁决设计

`policy.py` 中的 `evaluate_memory()` 被**调用两次**（初评 + 复评），这是系统的核心设计模式：

```
第一次调用（初评）: evaluate_memory(relation=None)
    │
    仅靠关键词匹配做快速分流
    目的：省去不必要的向量检索和 LLM 调用
    │
    ├── ignore / ask_confirmation → 直接返回，不进入后续流程
    └── auto_save → 进入后续流程（向量检索 + 冲突检测）

第二次调用（复评）: evaluate_memory(relation="duplicate" | "replace" | ...)
    │
    结合冲突检测结果做精细判断
    │
    ├── duplicate → ignore（无需重复存储）
    ├── replace/conflict → ask_confirmation（需用户裁决）
    └── complement/unrelated/无已有记忆 → auto_save
```

**初评规则**（无 relation，规则 1-3）：

| 优先级 | 条件 | 裁决 |
|:---:|------|------|
| 1 | 规则修改请求 | `route_rule_change` |
| 2 | 临时状态 | `ignore` |
| 3 | 敏感信息 | `ask_confirmation` |

**复评规则**（带 relation，规则 4-6）：

| 优先级 | 条件 | 裁决 |
|:---:|------|------|
| 4 | 语义重复 | `ignore` |
| 5 | 替换或冲突 | `ask_confirmation` |
| 6 | 默认 | `auto_save` |

## 13. 设计决策与权衡

### 13.1 为什么用两阶段策略（初评 + 复评）？

| 初评（无 relation） | 复评（带 relation） |
|---------------------|---------------------|
| 纯关键词匹配，极快（微秒级） | 结合 LLM 冲突检测结果，慢但精准 |
| 过滤掉明显需要忽略/确认的候选项 | 只对通过初评的候选项做精细判断 |
| 避免对每条候选项都做昂贵的向量检索和 LLM 调用 | 仅对需要写入的候选项投入高成本判断 |

### 13.2 为什么用两级冲突检测（向量初筛 + LLM 判定）？

- **第一级（向量相似度）**：零 LLM 调用，微秒级延迟。高相似度直接判 duplicate，覆盖大部分重复场景
- **第二级（LLM 语义判定）**：处理边界情况。向量相似度无法区分 complement vs replace vs conflict，只有 LLM 能理解语义差异

### 13.3 为什么 Curator 用本地 Ollama 而 ConflictDetector 用 DeepSeek？

| 组件 | LLM | 原因 |
|------|-----|------|
| Curator（提取） | Ollama Qwen2.5 7B | 提取任务相对机械（识别值得记忆的内容），本地模型足够胜任，零成本 |
| ConflictDetector（判定） | DeepSeek | 冲突判定需要精细的语义理解和推理，云端大模型效果更好 |

### 13.4 为什么 Curator 禁止自动更新/删除？

```
enable_updates=False
enable_deletes=False
```

Curator 只负责**新增**候选项。更新和删除是**破坏性操作**，必须由上层 Policy 在确认用户意图后执行。这避免了 LLM 误判导致用户记忆被意外覆盖或删除。

### 13.5 敏感记忆的两层防御

- **第一层**：Policy 关键词检测 — `is_sensitive_memory()` 快速拦截
- **第二层**：`create_memory_record(confirmed=True)` — 即使 Policy 漏判，工厂函数也会阻止写入

敏感记忆必须通过 `ask_confirmation → 用户确认 → confirmed=True` 的完整链路才能写入。

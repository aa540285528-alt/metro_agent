# static 设计说明

## 职责与边界

`static` 保存前端静态页面资源，当前核心是 `preview.html`。它为本地 Agent 服务提供聊天预览、RAG 引用展示、检索分数和后续评测指标监控界面的承载位置。

本目录只负责前端交互和展示，不直接实现 Agent 图编排、RAG 检索、数据库写入或离线评测计算。页面通过 API 获取数据，后端职责仍由对应 Python 模块承担。

## 主要组件

- `preview.html`：当前聊天和调试预览页面，承载用户输入、回答显示、引用文档、检索分数等 UI。

后续如果新增在线评测指标监视界面，可以继续在本目录扩展页面资源，或拆出更清晰的静态文件结构，例如 `css/`、`js/`、`pages/`。

## 数据流与生命周期

用户在页面输入问题后，前端调用后端聊天 API。后端执行 Agent 图、RAG、工具和 trace 记录后返回最终回答、引用文档和必要调试信息。页面负责把结果渲染出来。

在线评测指标页面的预期数据流是：后端从 `observability` 数据库或聚合服务读取 trace、token、耗时、工具调用和评测指标，前端只展示聚合结果和明细入口。

## 依赖与配置

`preview.html` 依赖后端 API 路径、浏览器运行环境和静态文件服务。页面不应内置 API key、模型密钥、数据库连接或本地绝对产物路径。

若需要展示 trace、RAG 指标或 token 成本，应由后端返回脱敏后的结构化 JSON，前端不直接读取 `artifacts/` 或数据库。

## 持久化与产物

本目录通常不保存运行数据。浏览器本地状态如输入框内容、临时 UI 状态或筛选项，可以使用页面内状态或 localStorage，但不能当作业务持久化来源。

聊天历史、trace、评测指标和评测产物分别由 `conversation_history`、`observability`、`evaluation` 和 `artifacts` 管理。

## 异常处理与测试策略

页面应能清晰展示后端请求失败、超时、空回答、无引用文档和评测指标不可用等状态。不要把所有失败都渲染成同一句不可诊断提示。

测试策略包括手动页面验证、API mock、关键 DOM 状态检查和浏览器截图检查。新增监控界面时，应特别检查移动端和桌面端布局不重叠、长文本不溢出。

## 维护建议

前端展示字段要跟后端响应契约同步演进。新增调试字段时优先放在可折叠区域，避免主聊天体验被大量内部指标淹没。

如果页面逻辑继续增长，应把脚本从单个 HTML 拆出模块化 JS/CSS，并为指标监控界面设计稳定的数据接口。

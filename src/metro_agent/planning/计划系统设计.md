# Planning 模块设计

日期：2026-07-06

## 1. 背景

当前系统已经具备基础的意图识别、`agent_order` 顺序路由、共享 State、专业 Agent、结果拼接、短期记忆和长期记忆能力。

现有编排方式只能生成 Agent 名称列表，例如：

```text
["realtime_agent", "knowledge_agent", "diagnosis_agent"]
```

该结构不能表达以下能力：

- 步骤之间的依赖关系；
- 无依赖任务的并行执行；
- 单步骤执行状态和证据；
- 失败重试、熔断和降级；
- 执行过程中根据新证据修改计划；
- 高风险步骤的人工确认；
- Review 不通过后的定向修复。

因此需要在 Supervisor 控制面中增加 Planning 子系统。

## 2. 目标

Planning 模块需要实现：

1. 简单问题继续走快速路由，避免不必要的规划开销。
2. 复杂任务由 Planner 生成结构化 DAG。
3. Scheduler 根据依赖关系并行派发就绪步骤。
4. 子 Agent 在单步骤内部按需采用 ReAct。
5. 所有步骤返回统一的 `StepResult`。
6. 执行失败时支持限次重试、熔断、降级、人工确认和重新规划。
7. Supervisor 聚合全部必要结果，独立 ReviewAgent 负责质量与安全审查。
8. 规划和执行状态写入中心 State，并通过 RedisSaver 持久化。

## 3. 非目标

第一阶段不处理以下内容：

- 完善全部意图分类规则；
- 会话问题枚举和 `turn_index`；
- PostgreSQL 完整会话历史；
- 跨多个用户共享执行计划；
- 保存模型内部思维链；
- 自动执行未经批准的高风险生产操作。

## 4. 总体架构

Supervisor 是逻辑控制中枢，但由多个职责单一的 LangGraph 节点共同实现。

```text
用户输入
   |
   v
IntentClassifier
   |
   +-- 信息不足 --> ClarificationManager --> interrupt --> 用户补充
   |
   +-- 简单任务 --> FastRouter --> 单Agent --> LightweightReview
   |
   +-- 复杂任务 --> Planner --> PlanValidator --> Scheduler
                                            |
                                            v
                                      ExecuteStep Workers
                                            |
                                            v
                                      ExecutionEvaluator
                                      /       |       \
                                   继续      Replan    降级/终止
                                      \       |       /
                                            v
                                      ResultAggregator
                                            |
                                            v
                                     IndependentReview
                                      /             \
                                   通过             不通过
                                    |                 |
                                    v                 v
                               FinalAnswer        Replanner
```

## 5. 三层执行模型

### 5.1 外层：Plan-and-Execute

负责复杂任务的生命周期：

```text
规划 -> 执行 -> 评估 -> 重规划/继续 -> 聚合 -> 审查
```

### 5.2 中层：DAG

DAG 表达步骤之间的依赖关系。没有未完成依赖的步骤可以并行执行。

示例：

```text
查询实时告警 ---------+
                      +--> 综合故障诊断 --> 安全审查 --> 最终回答
检索相关SOP ----------+
```

### 5.3 内层：ReAct

ReAct 只用于单个步骤内部的工具调用和观察反馈。

适用范围：

- RealtimeAgent：调用一个或多个网管工具；
- KnowledgeAgent：检索不足时改写查询并再次检索；
- DiagnosisAgent：必要时补充查询证据；
- GeneralAgent：通常不需要 ReAct；
- ReviewAgent：使用结构化审查，不调用业务工具。

State 只保存工具调用、工具结果、步骤状态、证据和简短执行说明，不保存模型内部思维链。

## 6. Supervisor 职责划分

Supervisor 逻辑控制面包含：

| 组件 | 职责 |
|---|---|
| IntentClassifier | 识别意图、复杂度和是否需要规划 |
| ClarificationManager | 判断缺失信息并发起澄清 |
| Planner | 将目标拆解为 DAG |
| PlanValidator | 校验计划结构与安全约束 |
| Scheduler | 找出并派发所有就绪步骤 |
| ExecutionEvaluator | 判断继续、重试、降级、等待人工或重规划 |
| Replanner | 基于执行结果生成新计划版本 |
| ResultAggregator | 汇总步骤结果并生成回答草稿 |
| QualityController | 根据 ReviewAgent 结论决定通过或重规划 |

ReviewAgent 保持独立，不合并进 Supervisor，避免系统自己生成、自己审查。

## 7. 数据模型

### 7.1 ExecutionPlan

```python
class ExecutionPlan(TypedDict):
    plan_id: str
    goal: str
    version: int
    status: str
    steps: list[PlanStep]
    created_at: str
    updated_at: str
```

计划状态：

```text
draft
validated
running
waiting_human
completed
failed
cancelled
```

### 7.2 PlanStep

```python
class PlanStep(TypedDict):
    step_id: str
    description: str
    agent: str
    dependencies: list[str]
    status: str
    expected_output: str
    input_refs: list[str]
    requires_approval: bool
    max_attempts: int
    timeout_seconds: int
```

步骤状态：

```text
pending
ready
running
success
failed
waiting_human
degraded
skipped
cancelled
```

### 7.3 StepResult

```python
class StepResult(TypedDict):
    step_id: str
    plan_version: int
    attempt: int
    status: str
    output: str
    evidence: list[dict]
    tool_results: list[dict]
    error: dict | None
    retryable: bool
    started_at: str
    completed_at: str
    duration_ms: int
```

错误对象至少包含：

```python
{
    "type": "timeout|tool_error|invalid_output|dependency_error|policy_block",
    "message": "...",
    "source": "agent_or_tool_name",
}
```

### 7.4 PlanEvent

```python
class PlanEvent(TypedDict):
    event_id: str
    plan_id: str
    plan_version: int
    event_type: str
    step_id: str | None
    detail: dict
    created_at: str
```

事件类型包括：

```text
plan_created
plan_validated
step_dispatched
step_succeeded
step_failed
step_retried
circuit_opened
plan_revised
human_requested
human_resumed
review_rejected
plan_completed
```

## 8. State 扩展

`MetroAgentState` 增加：

```python
planning_required: bool
normalized_goal: str
missing_information: list[str]
execution_plan: ExecutionPlan
step_results: dict[str, StepResult]
active_step_ids: list[str]
plan_version: int
plan_events: list[PlanEvent]
planning_error: str
replan_count: int
```

Reducer 规则：

- `step_results`：按 `step_id` 合并，较高 attempt 覆盖较低 attempt；
- `plan_events`：只追加，按时间排序；
- `execution_plan`：只接受更高 `version`，禁止旧计划覆盖新计划；
- `active_step_ids`：每次由 Scheduler 完整覆盖；
- `planning_error`：最新错误覆盖旧错误。

## 9. Planner 输出规则

Planner 使用结构化输出，不能返回自由文本计划。

Planner 必须：

1. 为每个步骤生成唯一 `step_id`；
2. 只使用允许的 Agent；
3. 明确所有依赖；
4. 让无依赖任务可并行；
5. 为步骤指定可验证的 `expected_output`；
6. 标记高风险步骤是否需要人工批准；
7. 不创建“思考”“分析一下”等不可验证步骤；
8. 不把最终答案步骤交给专业 Agent，最终聚合由 Supervisor 完成。

第一阶段允许的执行 Agent：

```text
knowledge_agent
realtime_agent
diagnosis_agent
general_agent
```

`review_agent` 由控制流程固定调用，不由 Planner 任意插入。

## 10. PlanValidator

计划执行前必须进行确定性校验。

校验内容：

1. `plan_id`、`step_id` 非空；
2. `step_id` 唯一；
3. Agent 位于允许列表；
4. 所有依赖步骤存在；
5. 步骤不能依赖自身；
6. DAG 不存在环；
7. 至少存在一个无依赖入口步骤；
8. `max_attempts` 和 `timeout_seconds` 在允许范围；
9. 高风险动作必须设置 `requires_approval=True`；
10. 计划步骤数不超过配置上限。

校验失败时不执行部分计划，而是把错误返回 Planner 修订。连续修订超过上限则降级为安全回答。

## 11. Scheduler

Scheduler 是确定性代码，不由 LLM 决定哪些步骤已经就绪。

步骤可执行条件：

```text
step.status == pending
AND 所有 dependencies 对应结果均为 success 或允许的 degraded
AND step 不在 active_step_ids
AND 未触发熔断
```

所有满足条件的步骤通过 LangGraph `Send` 动态并行派发。

并行 Worker 不直接覆盖同一个 State 字段。每个 Worker 只写入以 `step_id` 为键的 `step_results`，由 reducer 合并。

若没有可执行步骤，但计划尚未完成：

- 存在 `waiting_human`：进入人工确认；
- 存在失败依赖：进入 Replanner；
- 存在环或未知阻塞：标记规划错误并终止；
- 所有必要步骤完成：进入结果聚合。

## 12. ExecuteStep Worker

每次 Worker 只接收一个 `PlanStep` 和它声明的输入引用。

Worker 输入不包含完整中心 State，而是由上下文组装器按 Agent 预算构造：

```text
系统提示词
当前步骤描述
依赖步骤结果
必要的会话历史
必要的长期记忆
必要的工具/RAG上下文
```

执行完成后统一转换为 `StepResult`。

Agent 原有返回结构通过 Adapter 转换，不要求第一阶段立即重写全部 Agent。

## 13. Replanner

Replanner 的输入：

```text
原始目标
当前计划
成功步骤结果
失败步骤错误
剩余步骤
Review结论
熔断状态
用户补充信息
```

Replanner 可以：

- 修改未执行步骤；
- 新增补偿或补充检索步骤；
- 删除不再需要的未执行步骤；
- 修改依赖；
- 选择替代 Agent；
- 把步骤改为降级执行；
- 请求人工输入；
- 终止无法安全完成的计划。

Replanner 不得：

- 删除或篡改已成功的 `StepResult`；
- 把旧版本计划覆盖新版本；
- 绕过 ReviewAgent；
- 绕过需要人工批准的高风险步骤。

每次修改生成新的 `plan_version`。成功结果通过 `input_refs` 在新版本中复用。

默认限制：

```text
最大计划版本：3
单步骤最大尝试：2
整个计划最大步骤数：12
```

达到上限后停止自动循环，返回已完成内容、失败原因和人工处理建议。

## 14. 重试、熔断与降级

### 14.1 重试

只对可恢复错误重试：

- 网络超时；
- 临时服务不可用；
- 工具限流；
- 可修复的结构化输出错误。

以下错误不自动重试：

- 参数缺失；
- 权限不足；
- 安全策略禁止；
- 用户拒绝操作；
- 明确的业务不存在。

### 14.2 熔断

熔断对象是 Agent、工具或外部服务，不是整个计划。

熔断状态至少记录：

```text
failure_count
opened_at
cooldown_seconds
last_error
```

第一阶段先把熔断状态放在当前计划 State；后续可迁移到 Redis，使多个会话共享服务健康状态。

### 14.3 降级

示例：

- 实时网管不可用：明确无法确认当前状态，继续提供知识库 SOP 和离线排查建议；
- RAG 不可用：只基于工具事实和通用安全原则回答，并降低置信度；
- DiagnosisAgent 不可用：汇总现有证据，不生成未经验证的故障结论；
- Review 不通过：返回风险说明，禁止输出高风险操作指令。

降级结果必须标记 `status="degraded"`，最终回答必须说明缺失的数据源。

## 15. Human-in-the-loop

以下情况进入人工确认：

- 高风险设备操作；
- 需要修改生产配置；
- 计划缺少关键参数且不能安全推断；
- 多个证据冲突；
- 用户需要选择降级方案；
- 自动重规划达到上限。

节点使用 `interrupt()` 输出 JSON 可序列化的请求：

```python
{
    "type": "approval|clarification|choice",
    "plan_id": "...",
    "step_id": "...",
    "question": "...",
    "options": [...],
    "context": {...},
}
```

前端携带相同 `thread_id`，通过 `Command(resume=...)` 恢复。

`interrupt()` 之前的外部副作用必须幂等，因为恢复时节点会从头执行。

## 16. Review 与结果聚合

### 16.1 ResultAggregator

只聚合成功或允许降级的步骤：

- 按计划依赖关系组织证据；
- 标明实时数据、知识依据和诊断推断；
- 不把失败步骤伪装为成功；
- 生成待审查草稿。

### 16.2 IndependentReview

ReviewAgent 检查：

- 是否回答用户目标；
- 是否存在无证据结论；
- 是否错误使用过期实时数据；
- 引用和工具结果是否匹配；
- 是否遗漏失败或降级说明；
- 操作步骤是否安全；
- 输出格式是否符合要求。

Review 输出：

```python
{
    "decision": "pass|revise|replan|block",
    "issues": [...],
    "required_actions": [...],
}
```

处理方式：

- `pass`：返回最终答案；
- `revise`：Aggregator 在不新增事实的前提下修改表达；
- `replan`：需要新证据，进入 Replanner；
- `block`：阻止危险输出，返回安全说明。

## 17. LangGraph 组件映射

| Planning 能力 | LangGraph 组件 |
|---|---|
| 结构化计划 | 模型 `with_structured_output()` |
| 动态并行 Worker | `Send` |
| 更新 State 并跳转 | `Command(update=..., goto=...)` |
| 人工确认与澄清 | `interrupt()` |
| 恢复暂停任务 | `Command(resume=...)` |
| 状态持久化 | 当前 `RedisSaver` |
| Agent 内 ReAct | Agent 子图或工具循环 |

参考：

- https://docs.langchain.com/oss/python/langgraph/workflows-agents
- https://docs.langchain.com/oss/python/langgraph/graph-api
- https://docs.langchain.com/oss/python/langgraph/interrupts

## 18. 与当前 Graph 的集成

当前快速路径保留：

```text
classify_intent -> agent_router -> Agent -> review -> assemble
```

复杂路径新增：

```text
classify_intent
-> planner
-> plan_validator
-> scheduler
-> execute_step workers
-> execution_evaluator
-> scheduler/replanner/aggregator
-> review
-> final
```

`classify_intent` 后增加 `planning_required` 条件路由：

```text
False -> 现有 agent_router
True  -> planner
```

第一阶段不删除现有 `agent_order`，保证快速路径和旧功能继续工作。

## 19. 上下文与记忆

Planning 使用中心 State，但不同组件按需读取：

- Planner：用户目标、必要会话历史、关键实体、可用 Agent 能力；
- Scheduler：只读取计划和步骤结果，不调用 LLM；
- Worker：只读取当前步骤、依赖输出和 Agent 专属上下文；
- Replanner：读取计划、成功结果、失败错误、Review 意见；
- Aggregator：读取最终有效结果；
- ReviewAgent：读取用户目标、回答草稿和证据引用。

短期记忆压缩继续独立运行。Planning 不读取或保存模型内部推理，只保存结构化计划与执行事件。

## 20. 可观测性

每个计划至少记录：

```text
plan_id
plan_version
step_id
agent
attempt
status
duration_ms
error_type
tool_calls
token_allocation
review_decision
```

LangGraph Event 中应能看到计划创建、步骤派发、并行执行、重试、重规划、审查和完成。

## 21. 验收场景

### 21.1 简单任务

输入：

```text
LTE是什么？
```

期望：

- `planning_required=False`；
- 不生成 ExecutionPlan；
- 快速路由到单 Agent；
- 经过轻量 Review 后回答。

### 21.2 并行复杂任务

输入：

```text
查询11号线赤沙站无线系统当前告警，结合SOP分析掉线原因并给出处理建议。
```

期望：

- 生成 DAG；
- Realtime 与 Knowledge 并行；
- Diagnosis 等待两个步骤；
- Aggregator 汇总；
- Review 通过后回答。

### 21.3 可重试故障

Realtime 工具第一次超时、第二次成功：

- 第一次生成 failed StepResult；
- 标记 `retryable=True`；
- 只重试该步骤；
- 不重复执行已成功 Knowledge 步骤。

### 21.4 熔断与降级

实时接口连续失败：

- 打开实时工具熔断；
- 不再继续请求该接口；
- 使用知识库与离线诊断生成降级回答；
- 明确说明无法确认当前实时状态。

### 21.5 人工确认

计划包含生产配置修改：

- 执行前进入 `interrupt()`；
- 使用相同 `thread_id` 和 `Command(resume=...)` 恢复；
- 用户拒绝时步骤标记 cancelled，不执行工具。

### 21.6 Review 重规划

Review 发现诊断结论缺少实时证据：

- 返回 `decision="replan"`；
- Replanner 增加补充实时查询步骤；
- 已成功知识检索结果继续复用。

## 22. 实施边界与顺序

Planning 模块按以下顺序实施：

1. 数据模型和 reducer；
2. Planner 结构化输出；
3. PlanValidator；
4. 顺序 Scheduler 和 StepResult Adapter；
5. DAG 就绪判断；
6. `Send` 并行执行；
7. ExecutionEvaluator 与限次重试；
8. Replanner 与计划版本；
9. ResultAggregator；
10. 独立 Review 决策；
11. 熔断和降级；
12. `interrupt` Human-in-the-loop；
13. 可观测性和旧路径兼容验收。

# conversation_history 设计说明

## 职责与边界

`conversation_history` 负责对话历史的数据库模型、连接管理和服务封装，为 Agent 提供短期或长期上下文所需的历史消息能力。它关注"对话记录怎么存、怎么查、怎么提供给上层"，不负责 Agent 规划、RAG 检索、trace 记录或评测计算。

该模块是业务持久化层的一部分，应保持接口稳定，让 API、Agent 服务和图节点通过服务函数访问历史数据，而非直接操作 SQLAlchemy model。

---

## 目录结构


## 各组件详解

### 1. `database.py` — 数据库连接管理

```python
engine = create_engine(os.environ["DATABASE_URL"], pool_pre_ping=True)
SessionLocal = sessionmaker(bind=engine)
```

**设计决策：**

| 决策 | 说明 |
|---|---|
| **模块级 engine 创建** | 导入时即从环境变量 `DATABASE_URL` 读取并创建 engine，失败立即报错（fail-fast），避免运行时才发现配置缺失 |
| **`pool_pre_ping=True`** | 每次从连接池取出连接时先发一条 `SELECT 1` 探测连接是否仍然有效，防止因数据库重启/超时导致的 `OperationalError` |
| **`sessionmaker` 暴露为 `SessionLocal`** | 不绑定具体 Session 实例，每次调用方通过 factory 创建独立 Session，保证线程/请求间隔离 |
| **不在本文件做日志配置** | 日志由 `alembic.ini` 或调用方统一管理，保持 database.py 的单一路径 |

### 2. `models.py` — SQLAlchemy ORM 模型

#### `Base` — 声明基类

```python
class Base(DeclarativeBase):
    pass
```

- 所有模型的公共基类，其 `Base.metadata` 被 Alembic 的 `env.py` 导入为 `target_metadata`
- `observability.models` 模块中的表也注册到同一个 `Base.metadata`，因为它们 import 时会执行类定义

#### `Conversation` — 对话会话表（`conversations`）

| 列 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | `Mapped[str]` → `String(128)` | PK | 对话唯一标识（thread_id），由调用方生成 |
| `owner_id` | `Mapped[str]` → `String(128)` | NOT NULL | 所属用户 ID，所有查询均限定 owner |
| `title` | `Mapped[str]` → `String(40)` | NOT NULL | 对话标题，限制 40 字符 |
| `is_pinned` | `Mapped[bool]` → `Boolean` | NOT NULL, `default=False` | 是否置顶 |
| `pinned_at` | `Mapped[datetime \| None]` → `DateTime(tz=True)` | NULLABLE | 置顶操作时间，NULL 表示未置顶 |
| `created_at` | `Mapped[datetime]` → `DateTime(tz=True)` | NOT NULL, `server_default=func.now()` | 创建时间，由数据库填充 |
| `updated_at` | `Mapped[datetime]` → `DateTime(tz=True)` | NOT NULL, `server_default=func.now()`, **`onupdate=func.now()`** | 最后更新时间，每次 UPDATE 自动刷新 |

**ORM 关系：**
```python
messages: Mapped[list[ConversationMessage]] = relationship(
    back_populates="conversation",
    cascade="all, delete-orphan",
    order_by="ConversationMessage.id",
)
```

- `cascade="all, delete-orphan"`：删除 Conversation 时级联删除所有消息；从 `messages` 列表中移除的消息对象会在 flush 时被 DELETE
- `order_by="ConversationMessage.id"`：通过 `conversation.messages` 访问时自动按 ID 升序（即时间顺序）

**复合索引 `ix_conversations_owner_sort`：**
```python
Index("ix_conversations_owner_sort", "owner_id", "is_pinned", "pinned_at", "updated_at")
```

专门为 `list_conversations` 的查询模式设计：`WHERE owner_id = ? ORDER BY is_pinned DESC, pinned_at DESC, updated_at DESC`，索引列顺序与排序顺序精确匹配，可完全避免 filesort。

#### `ConversationMessage` — 对话消息表（`conversation_messages`）

| 列 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | `Mapped[int]` → `Integer` | PK, AUTOINCREMENT | 消息自增 ID，同时作为时间顺序的依据 |
| `conversation_id` | `Mapped[str]` → `ForeignKey("conversations.id", ondelete="CASCADE")` | NOT NULL, INDEXED | 关联的对话，级联删除 |
| `role` | `Mapped[str]` → `String(16)` | NOT NULL | 角色：`"user"` 或 `"assistant"` |
| `content` | `Mapped[str]` → `Text` | NOT NULL | 消息正文，无长度限制 |
| `created_at` | `Mapped[datetime]` → `DateTime(tz=True)` | NOT NULL, `server_default=func.now()` | 消息时间戳 |

`ForeignKey("conversations.id", ondelete="CASCADE")` 在数据库层保证删除 Conversation 时自动删除关联消息，配合 ORM 层的 `cascade="all, delete-orphan"` 形成双重保护。

### 3. `service.py` — 业务服务层

服务层采用 **DTO + Service** 模式，所有对外暴露的数据结构都是 frozen dataclass，服务方法通过 session factory 注入实现数据访问。

#### 异常

```python
class ConversationNotFound(Exception):
    pass
```

- 当 `thread_id` 不存在或 `owner_id` 不匹配时抛出
- 不区分"不存在"和"无权限"——统一返回 404 语义，避免通过异常消息泄漏其他用户是否存在

#### 数据传输对象（DTO）

三个 frozen dataclass 构成从服务层到调用方的不可变数据契约：

```python
@dataclass(frozen=True)
class ConversationSummary:
    id: str
    title: str
    is_pinned: bool
    updated_at: datetime
```

用于列表接口，不含消息内容，减少数据传输量。

```python
@dataclass(frozen=True)
class StoredMessage:
    role: Literal["user", "assistant"]
    content: str
    created_at: datetime
```

单条消息，`role` 限定为 `Literal["user", "assistant"]`，类型层面禁止了无效值。

```python
@dataclass(frozen=True)
class ConversationDetail:
    id: str
    title: str
    is_pinned: bool
    messages: list[StoredMessage]
```

用于详情接口，包含完整消息列表。

#### `ConversationHistoryService` 类

**构造函数：**
```python
def __init__(self, session_factory: sessionmaker[Session]) -> None:
    self._session_factory = session_factory
```

通过依赖注入接收 `sessionmaker`，而非硬编码导入 `database.SessionLocal`。这使得单元测试可以注入绑定到 SQLite in-memory 的 session factory，无需真实数据库。

---

**静态辅助方法：**

##### `_as_utc(value: datetime) -> datetime`

将 datetime 归一化到 UTC：
- 若传入的是 naive datetime（无时区），视为 UTC 并附加 `timezone.utc`
- 若传入的是 aware datetime，通过 `astimezone` 转换

保证 API 响应中的时间戳始终带有时区信息且为 UTC。

##### `_to_summary(conversation: Conversation) -> ConversationSummary`

ORM 对象到 DTO 的映射，集中处理时区归一化，避免各方法重复。

##### `_get_owned_conversation(session, thread_id, owner_id) -> Conversation`

按 `thread_id + owner_id` 联合查询，未找到则抛出 `ConversationNotFound`。所有需要先查后改的操作（update、delete）复用此方法。

---

**公开方法：**

##### `record_turn(thread_id, owner_id, user_content, assistant_content) -> ConversationSummary`

原子记录一轮对话（一条 user + 一条 assistant）：

```
┌─────────────────────────────────────────────┐
│ 1. strip 输入，验证非空                       │
│ 2. 在事务中查询 Conversation                  │
│    ├── 不存在 → 自动创建，title = 前40字       │
│    ├── 存在但 owner 不匹配 → ConversationNotFound │
│    └── 存在且 owner 匹配 → 更新 updated_at     │
│ 3. 批量插入两条 ConversationMessage            │
│ 4. flush 后返回 ConversationSummary           │
└─────────────────────────────────────────────┘
```

**关键设计细节：**

- `session_factory.begin()` 开启事务，整个方法在同一个数据库事务中——如果插入消息失败，`updated_at` 也不会被修改
- 新对话的 `title` 从第一条 user 消息截取前 40 个字符：`" ".join(user_content.split())[:40]`——先做 whitespace 归一化再截断，避免标题以空格开头
- 通过 `owner_id` 校验保证用户只能向自己拥有的对话写入消息

##### `list_conversations(owner_id) -> list[ConversationSummary]`

列出某用户的所有对话，按以下优先级排序：

```sql
ORDER BY is_pinned DESC, pinned_at DESC, updated_at DESC, id ASC
```

| 排序层级 | 效果 |
|---|---|
| `is_pinned DESC` | 置顶对话在最前 |
| `pinned_at DESC` | 最近置顶的优先 |
| `updated_at DESC` | 最近活跃的优先 |
| `id ASC` | 同时间戳时按创建先后（确定性排序） |

该排序精确命中复合索引 `ix_conversations_owner_sort`。

##### `get_conversation(thread_id, owner_id) -> ConversationDetail`

获取单个对话的完整内容（含所有消息）。

- 使用 `selectinload(Conversation.messages)` 进行**急加载**：一次附加 SELECT 拉取所有关联消息，避免遍历 `conversation.messages` 时触发 N+1 查询
- 消息在 ORM 层按 `order_by="ConversationMessage.id"` 排序，保证时间顺序
- `owner_id` 校验保证数据隔离

##### `update_conversation(thread_id, owner_id, *, title=None, is_pinned=None) -> ConversationSummary`

部分更新对话属性：

| 参数 | 校验 | 行为 |
|---|---|---|
| `title` | 1–40 字符 | 覆盖 title |
| `is_pinned` | `bool \| None` | `True` → 设置 `pinned_at = now()`；`False` → 清除 `pinned_at = None` |

- 使用 keyword-only 参数（`*` 之后），调用方必须显式命名参数
- `session_factory.begin()` 内执行，事务保护
- 更新后刷新 `updated_at`

##### `delete_conversation(thread_id, owner_id) -> None`

删除对话，级联删除所有消息（数据库层 `ON DELETE CASCADE` + ORM 层 `cascade="all, delete-orphan"` 双重保证）。

## 数据流与生命周期

```
用户发起请求
    │
    ▼
API / Agent 入口
    │
    ├──[请求开始]──────────────────────────────┐
    │  ConversationHistoryService              │
    │    .get_conversation(thread_id, uid)     │
    │    → ConversationDetail                  │
    │    → 提取 messages 构建对话上下文         │
    └──────────────────────────────────────────┘
    │
    ▼
Agent 图执行（planner → agents → tools → aggregate）
    │  中间节点不直接操作 conversation_history
    │
    ▼
    ├──[请求结束]──────────────────────────────┐
    │  ConversationHistoryService              │
    │    .record_turn(thread_id, uid,          │
    │       user_content, assistant_content)   │
    │    → ConversationSummary                 │
    └──────────────────────────────────────────┘
    │
    ▼
响应返回给用户
```

**关键约定：**
- 请求开始：加载上下文（`get_conversation`）
- 请求结束：记录最终回答（`record_turn`）
- 中间节点不应直接绕过服务层写数据库——只用 Service 的公开方法

## 多租户隔离设计

所有涉及对话操作的方法都要求同时传入 `thread_id` 和 `owner_id`：

| 方法 | 隔离方式 |
|---|---|
| `record_turn` | 新建对话时绑定 owner；写入时校验 owner 是否匹配 |
| `list_conversations` | WHERE owner_id = ? |
| `get_conversation` | WHERE id = ? AND owner_id = ? |
| `update_conversation` | `_get_owned_conversation` 校验 |
| `delete_conversation` | `_get_owned_conversation` 校验 |

"不存在"和"属于其他用户"统一映射为 `ConversationNotFound`，不泄漏其他用户是否有同名对话。

| `SQLAlchemy` | ORM 框架，模型定义和查询 |

## 异常处理与测试策略

### 异常处理

| 场景 | 行为 |
|---|---|
| `DATABASE_URL` 未设置 | 模块导入时 `KeyError`，立即失败（fail-fast） |
| 数据库连接失败 | `OperationalError`，由 `pool_pre_ping=True` 缓解连接失效，但仍会向上传播 |
| 写入失败 | 事务回滚，异常向上传播，让上层感知历史保存失败 |
| 读取失败 | 异常向上传播；特殊的降级策略由调用方决定（如对话不存在时可降级为空上下文） |
| 空消息写入 | `ValueError("conversation messages must not be blank")` |
| 标题超长 | `ValueError("title must contain 1 to 40 characters")` |
| 对话不存在/无权限 | `ConversationNotFound(thread_id)` |

### 事务管理

`record_turn`、`update_conversation`、`delete_conversation` 使用 `session_factory.begin()` 自动管理事务边界：
- 进入 `with` 块 → `BEGIN`
- 正常退出 → `COMMIT`
- 异常退出 → `ROLLBACK`

`list_conversations` 和 `get_conversation` 使用 `session_factory()`（无 `begin`），因为它们是只读操作，无需显式事务。

### 测试策略

| 测试类型 | 方法 | 验证目标 |
|---|---|---|
| **消息写入** | 调用 `record_turn`，查询数据库验证两条消息均已持久化 | 原子写入正确 |
| **自动创建对话** | 对不存在的 thread_id 调用 `record_turn`，验证 Conversation 和 title 自动生成 | 新对话创建路径 |
| **按会话读取** | 写入多轮后调用 `get_conversation`，验证消息顺序和内容 | 读取完整性和排序 |
| **列表排序** | 创建多个对话（不同 pin 状态和时间），调用 `list_conversations`，验证排序 | 复合索引覆盖排序 |
| **Owner 隔离** | 用 owner A 写入，owner B 读取，验证抛出 `ConversationNotFound` | 多租户隔离 |
| **级联删除** | `delete_conversation` 后查询 `conversation_messages` 表，验证消息被级联删除 | 级联约束生效 |
| **标题校验** | 传入空字符串 / 41 字符标题，验证抛出 `ValueError` | 输入校验 |
| **时区归一化** | 写入带不同时区的 datetime，验证 `_as_utc` 输出一致 | UTC 归一化 |
| **Session 注入** | 在单元测试中注入 SQLite in-memory 的 sessionmaker | 不依赖生产数据库 |
| **更新 `updated_at`** | 写入消息后检查 `updated_at` 是否更新为最新时间 | `onupdate` 和手动设置均生效 |
| **置顶/取消置顶** | 连续切换 `is_pinned`，验证 `pinned_at` 的正确设置和清除 | pin 状态管理 |

## 维护建议

1. **新增历史字段时同步更新模型、服务层、迁移脚本和相关测试**。例如添加 `Conversation.tags` 字段需要同时修改 `models.py`（列定义）、`service.py`（DTO 和 update 方法）、`alembic/versions/`（新迁移）、以及相关测试。

2. **避免让调用方直接操作 SQLAlchemy model**：`__init__.py` 刻意不导出 ORM 类和 `SessionLocal`，调用方只能通过 `ConversationHistoryService` 访问数据。这保证了后续切换存储或增加审计逻辑时只需修改 service 层。

3. **对话历史可能是敏感数据**：调试日志里不要打印完整用户原文和完整回答内容。Service 方法目前不产生日志——如需添加，应只记录 thread_id 和角色，不记录 content。

4. **`Conversation.title` 的 40 字符限制**由数据库列定义和 service 层双重校验。自动生成标题时使用 `" ".join(user_content.split())[:40]` 先做空白归一化——如果将来修改生成逻辑，应保持这一惯例。

5. **`updated_at` 的双重更新时间**：ORM 层 `onupdate=func.now()` 提供自动更新，service 层在 `record_turn` 和 `update_conversation` 中手动设置——两者效果一致，但手动设置更显式，避免依赖 ORM 隐式行为。

6. **Session 生命周期遵循"请求内创建、请求结束关闭"**：`sessionmaker` 不做跨请求复用；每个 service 调用创建独立 session 并在 `with` 退出时自动关闭。不要在请求间共享 session。

7. **数据库迁移依赖本模块的模型定义**：Alembic 的 `env.py` 导入 `conversation_history.models.Base` 以获取 `target_metadata`。新增模型类时需确保它们继承自此 `Base`，否则不会被迁移检测到。

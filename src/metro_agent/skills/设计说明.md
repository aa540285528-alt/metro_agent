# Agents_skills 设计说明

## 职责与边界

`Agents_skills` 放置 Agent 可复用能力的本地实现，当前主要承担“诊断类技能”和技能运行时的组织职责。它面向上层 Agent 编排层提供可调用能力，不负责对话入口、状态机流转、数据库持久化或 RAG 索引构建。

本目录适合沉淀可被多个 Agent 或节点复用的领域技能。与 `Agents_tools` 的区别是：这里更偏 Agent 语义能力和流程片段，`Agents_tools` 更偏外部工具、RAG 工具、离线索引与评测脚本。

## 主要组件

- `skill_runtime.py`：技能运行时封装，负责技能注册、调度或统一调用入口。
- `diagnosis/`：诊断相关技能目录，承载故障分析、状态判断等能力。
- `__pycache__/`：Python 运行缓存，不属于源代码设计内容。

## 数据流与生命周期

上层 Agent 或节点在需要领域技能时调用本目录暴露的运行时能力。输入通常来自 Agent state、用户问题、工具返回或诊断上下文，输出再回到主状态流中，由图编排层决定是否继续规划、调用工具或生成最终回答。

技能本身应保持轻状态。跨轮对话记忆、链路追踪、工具调用记录和评测数据不在本目录保存，分别由 `conversation_history`、`observability`、`Agents_tools` 或 `evaluation` 负责。

## 依赖与配置

本目录应尽量依赖项目内部稳定接口，避免直接读取 `.env` 或硬编码模型、数据库、索引路径。确实需要配置时，应由调用方注入参数，或通过项目已有配置层传入。

诊断技能如果需要调用工具，应优先走已有工具封装，避免在技能内部直接创建网络客户端、数据库连接或向量索引实例。

## 持久化与产物

本目录默认不产生持久化数据。技能执行过程中的诊断结论应作为 Agent state、trace event 或最终回答的一部分向外返回。

如未来需要保存诊断报告，应优先写入 `artifacts/` 下的版本化产物，或通过 `observability` 的 trace artifact 机制记录，而不是在技能目录内生成运行文件。

## 异常处理与测试策略

技能内部异常应转化为可解释的失败信息，并让上层图节点决定重试、降级或终止。不要吞掉异常后返回看似成功的结果。

测试应覆盖技能的纯函数逻辑、异常路径和与上层 state 的契约。若技能依赖外部工具，应使用 mock 或 fixture，避免测试依赖真实网络、真实云模型或真实数据库。

## 维护建议

新增技能时保持目录边界清晰：技能只表达“怎么做某类 Agent 能力”，不顺手承担 API、页面、数据库或索引构建逻辑。

如果某个技能开始频繁读写文件、调用外部服务或维护复杂配置，应评估是否拆到 `Agents_tools` 或独立服务层，再由技能调用。

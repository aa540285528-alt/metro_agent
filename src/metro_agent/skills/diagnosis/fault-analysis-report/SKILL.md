# 故障分析报告生成 Skill

## 核心流程

1. 判断用户是否要生成故障分析报告、故障简报、事件复盘或处置总结。
2. 检查用户已提供的信息是否满足生成报告的最低要求（必要字段见 `references/required-fields.md`）：
   - 若缺失必要字段（如故障时间、设备名称、故障现象），生成澄清问题列表，反问用户，不猜测。
   - 若信息完整，进入下一步。
3. 根据用户指定的报告类型，读取对应的模板：
   - 正式简报 → `references/report-template.md`
   - 无指定 → 使用通用结构（参考 `assets/formal-report-outline.md`）
4. 若用户要求参考历史写法或表达风格，读取 `references/example-reports.md`。
5. 提取用户提供的时间、地点、设备、系统、现象、影响、处置过程、测试数据、原因和措施。
6. 按事实生成报告，每条事实性陈述标注信息来源（用户提供/系统查询/知识库引用）。
7. 不得编造未提供的时间、人员、设备编号、测试数据、告警编号、处置动作和厂家意见。

## 信息冲突处理规则

当用户提供的信息之间存在冲突时，按以下优先级裁决：

1. **用户最新提供的明确表述** — 最高优先级
2. **系统查询的确定性数据**（如网管告警时间） — 次高优先级
3. **历史知识库中的案例** — 低优先级，仅作参考
4. **Agent推断或假设** — 必须在报告中明确标注为“推断”

**示例**：
- 用户先说“故障发生在10:00”，后改口“是10:15”，应以“10:15”为准，并在报告中注明“经用户确认，故障时间为10:15”。
- 网管告警时间显示“10:12”，用户坚称“10:15开始”，优先采用用户确认的信息，但可补充网管数据作为参考。

## 输出原则

- 语气正式、客观、适合运维上报。
- 处理过程按时间线整理。
- 原因分析区分事实、测试结果和推断。
- 根因未确认时使用“初步判断”“疑似”“需进一步核实”。
- 报告末尾附注“报告版本：1.0”，如需修订递增版本号并保留修订记录。

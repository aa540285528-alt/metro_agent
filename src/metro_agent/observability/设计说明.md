# observability 设计说明

## 职责与边界

`observability` 负责 Agent 全链路追踪、节点耗时、工具调用、token 使用、成本归集、错误分类、trace evidence 签名、在线指标查询和评测结果持久化。它是当前项目建立 Agent 评估体系和线上监控界面的核心后端模块。

本目录不生成最终业务回答，不直接执行 RAG 检索，也不保存完整对话历史。它记录的是**执行过程证据**，供排障、监控、DeepEval 评测和后续在线评测页面使用。

与 `conversation_history` 的关系是**并列而非替代**：`conversation_history` 保存对话**内容**（谁说了什么），`observability` 保存执行**路径**（spans、tools、tokens、errors）。两者通过 `thread_id` / `trace_id` 关联。

## 各组件详解

### 1. `trace_types.py` — TraceEvent 不可变事件

整个可观测体系的**基本数据单元**，表示一次执行事件（如 agent 调用、LLM 调用、工具调用、RAG 检索）。

```python
@dataclass(frozen=True, slots=True)
class TraceEvent:
    trace_id: str
    span_id: str
    parent_span_id: str | None
    event_type: str
    status: str              # "running" → "success" / "failed"
    started_at: str          # ISO 8601 UTC
    finished_at: str | None
    duration_ms: float | None
    agent: str | None
    step_id: str | None
    attempt: int | None
    attributes: Mapping[str, Any]  # JSON-compatible frozen dict
    artifact_uri: str | None
    _started_perf_ns: int    # 高精度计时（不对外暴露）
```

#### 生命周期：`start()` → `finish()`

```
TraceEvent.start(trace_id, span_id, event_type, ...)
    │  验证 trace_id/span_id/event_type 为非空字符串
    │  验证 attempt >= 0
    │  status = "running"
    │  started_at = UTC ISO timestamp
    │  _started_perf_ns = perf_counter_ns()  ← 高精度起始时间
    │  attributes = JSON 序列化 → 反序列化 → MappingProxyType（冻结 + 净化）
    ▼
TraceEvent (frozen, running)
    │
    │  .finish(status, attributes, artifact_uri)
    │      验证 status 为非空字符串
    │      duration_ms = (perf_counter_ns() - _started_perf_ns) / 1_000_000
    │      attributes = merge(old, new) → JSON round-trip → MappingProxyType
    │      返回 new TraceEvent (frozen, finished)
    ▼
TraceEvent (frozen, finished)
```

**关键设计：**
- `_started_perf_ns` 使用 `perf_counter_ns()`（单调时钟），不受系统时间调整影响，保证 duration 精确
- `attributes` 在 start 和 finish 时各做一次 JSON round-trip：`json.dumps → json.loads → MappingProxyType`，确保只有 JSON 兼容的数据可进入 event，防止 ORM 对象、datetime 等不可序列化类型泄漏
- `MappingProxyType` 提供不可变字典，防止调用方意外修改已记录的属性

### 2. `models.py` — 数据库模型

9 个 SQLAlchemy ORM 模型，均继承自 `conversation_history.models.Base`，共享同一个 `DeclarativeBase.metadata`（被 Alembic `env.py` 引用）。

#### 模型关系图

```
AgentTrace (1) ──→ (*) AgentSpan (1) ──→ (*) LlmUsage
                    │                    └─→ (*) ToolCall
                    │ (自引用 FK)          └─→ (*) RagRetrieval
                    │ parent_span_id
                    └──→ AgentSpan (same trace)
                    
EvalRun (1) ──→ (*) EvalCaseResult

ChunkBuild (1) ──→ (*) ChunkItem
```

#### 五层可观测数据模型

| 模型 | 表 | 主键 | 核心外键 |
|---|---|---|---|
| `AgentTrace` | `agent_traces` | `id` (String 128) | — |
| `AgentSpan` | `agent_spans` | `(trace_id, span_id)` | FK → `agent_traces.id` CASCADE；自引用 FK `(trace_id, parent_span_id)` |
| `LlmUsage` | `llm_usages` | `id` (Integer auto) | FK `(trace_id, span_id)` → `agent_spans` CASCADE |
| `ToolCall` | `tool_calls` | `id` (Integer auto) | FK `(trace_id, span_id)` → `agent_spans` CASCADE |
| `RagRetrieval` | `rag_retrievals` | `id` (Integer auto) | FK `(trace_id, span_id)` → `agent_spans` CASCADE |

**关键设计：**
- `AgentSpan` 的自引用外键 `fk_agent_spans_parent_same_trace`：约束 `(trace_id, parent_span_id)` 引用 `(trace_id, span_id)`，保证父 span 和子 span 必须在同一个 trace 内
- 所有子表（LlmUsage、ToolCall、RagRetrieval）的外键使用复合外键 `(trace_id, span_id)` 指向 `agent_spans` 的复合主键，并设置 `ON DELETE CASCADE`
- `evaluation_service.py` 写入的 `EvalRun` / `EvalCaseResult` 和 `ChunkBuild` / `ChunkItem` 也在本模块定义（统一管理所有持久化模型）

### 3. `service.py` — Trace 存储与服务

#### `TraceStore` 协议

定义了 8 个方法的标准接口，使上层 `TraceRecorder` 不依赖具体存储实现：

```python
class TraceStore(Protocol):
    def create_trace(self, trace_id, request_attributes, started_at) -> bool: ...
    def append_span(self, event: TraceEvent) -> bool: ...
    def append_llm_usage(self, values) -> bool: ...
    def append_tool_call(self, values) -> bool: ...
    def append_rag_retrieval(self, values) -> bool: ...
    def finish_trace(self, trace_id, status, summary, finished_at) -> bool: ...
    def update_trace_summary(self, trace_id, summary) -> bool: ...
    def update_span_artifact(self, trace_id, span_id, artifact_uri, attributes) -> bool: ...
```

#### 三种存储实现

| 实现 | 类 | 说明 |
|---|---|---|
| **SQLAlchemy** | `SqlAlchemyTraceStore` | 默认，写入真实数据库，`_write()` 方法统一处理 session/commit/rollback/close |
| **内存** | `InMemoryTraceStore` | 测试用，所有数据存在 dict/list 中，`RLock` 保护并发 |
| **不可用降级** | `_UnavailableTraceStore` | 所有方法返回 False，当数据库初始化失败时自动使用 |

**`SqlAlchemyTraceStore._write()` 的错误处理：**
```python
def _write(self, operation):
    session = self._session_factory()
    try:
        operation(session)
        session.commit()
    except Exception as error:
        primary_error = error    # 记录错误
        try: session.rollback()  # 尝试回滚
        except: ...
    finally:
        try: session.close()     # 确保关闭
        except: ...
    self.last_error = type(primary_error).__name__
    return primary_error is None
```

每个 `_write()` 调用记录 `last_error` 和 `cleanup_errors`，供外部诊断，但**不向上传播异常**——保证了数据库故障不影响业务请求的正常响应。

#### `TraceRecorder` — 核心采集器

线程安全（`RLock` + `Condition`），管理一个 trace 的完整生命周期：

**内部状态：**

| 属性 | 说明 |
|---|---|
| `_active_span_ids` | 当前活跃（未完成）的 span ID 集合 |
| `_known_span_ids` | 已持久化到 store 的 span ID 集合 |
| `_completed_events` | 已完成事件的 dict 列表（用于 evidence snapshot） |
| `_recorded_llm_usages` | 已记录的 LLM 用量列表 |
| `_recorded_tool_calls` | 已记录的工具调用列表 |
| `_total_tokens` | 累计 token 数 |
| `_estimated_cost` | 累计费用 |

**`span()` 上下文管理器：**

```python
with recorder.span("agent", agent="knowledge_agent", step_id="step_1") as span:
    # 业务逻辑
    span.record_llm_usage(model="deepseek-v4", prompt_tokens=100, ...)
    span.record_tool_call(tool_name="query_alarm", status="success", ...)
    span.set_result("success", {"output_length": 512})
```

- 进入 `with` 块：创建 `TraceEvent.start()` → 加入 `_active_span_ids`
- 正常退出：调用 `_complete_span()`，finish event → 写入 store → 刷新 observations → 从 `_active_span_ids` 移除 → `notify_all()`
- 异常退出：`_complete_span(status="failed", attributes={"error_type": ...})` → 重新抛出原始异常
- 若 `recorder` 已 `finished` 或 `closing` → 返回 `event=None` 的空 span（静默跳过）

**`finish()` 方法的关闭协调：**

```
finish(status, summary)
    │
    ├── 设置 _closing = True
    ├── 等待 _active_span_ids 清空（最长 _finish_wait_timeout_seconds 秒）
    │     └── Condition.wait() 被 _complete_span() 中的 notify_all() 唤醒
    ├── 若超时 → 记录 trace_close_timeout + unfinished_span_count
    ├── 设置 _finished = True
    ├── 调用 store.finish_trace()
    └── 记录 _finish_persisted 标志
```

这种设计确保 `finish()` 在所有 span 完成（或超时）后才生成最终 summary，避免丢失尚未结束的 span 数据。

**`evidence_snapshot()`：** 返回 spans、llm_usages、tool_calls、errors 的内存快照，供 `finalize_node.py` 构建本地 trace evidence artifact。

#### `TraceRegistry` — 全局注册与并发协调

```
TraceRegistry (module-level singleton via get_trace_registry())
    │
    ├── start(trace_id, request_attributes) → TraceRecorder
    │     并发安全：若同一 trace_id 正被另一个线程 start，
    │     第二个线程等待 Event.set() 后返回同一个 recorder
    │     store 初始化失败 → 透明降级为 _UnavailableTraceStore
    │
    ├── get(trace_id) → TraceRecorder | None
    │
    └── finish(trace_id, status, summary) → bool
         从 registry 中移除该 recorder
```

### 4. `llm_usage.py` — Token 用量提取

**跨 provider 响应的归一化层。** 不同 LLM provider（OpenAI、DeepSeek、Qwen）的响应结构不同，token 字段命名各异，本模块统一提取为标准格式。

#### 多 provider 字段映射

```python
_PROMPT_TOKEN_KEYS = ("prompt_tokens", "input_tokens", "input_token_count")
_COMPLETION_TOKEN_KEYS = ("completion_tokens", "output_tokens", "output_token_count")
_TOTAL_TOKEN_KEYS = ("total_tokens", "total_token_count")
_CACHED_TOKEN_KEYS = ("cached_tokens", "cached_input_tokens", "cache_read_input_tokens")
_MODEL_KEYS = ("model", "model_name", "model_id")
_COST_KEYS = ("estimated_cost", "total_cost", "cost_usd", "cost")
```

#### `extract_llm_usage()` 提取流程

```
response (LangChain AIMessage / dict / raw object)
    │
    ▼
_response_mappings(): 遍历 response 的多个路径收集 metadata + usage dicts
    ├── response 本身（若是 Mapping）
    ├── response.response_metadata / additional_kwargs
    ├── response.usage_metadata（LangChain 直接属性）
    └── metadata 中嵌套的 usage_metadata / usage / token_usage
    │
    ▼
_first_token_count(): 按优先级匹配 PROMPT/COMPLETION/TOTAL/CACHED keys
    ├── prompt_tokens 或 completion_tokens 缺失 → 尝试从 total × known 推算
    ├── 推算失败或为负 → 返回 None
    ▼
_first_cost(): 搜索 metadata + usage 中的 cost 字段
    │  支持嵌套: {"total_cost": {"total": 0.123}} 或 {"estimated_cost": 0.123}
    ▼
返回: {model, prompt_tokens, completion_tokens, total_tokens?,
        cached_tokens?, reasoning_tokens?, estimated_cost?}
        或 None（提取失败）
```

**`record_llm_usage()`：** 将 `extract_llm_usage()` 的结果通过 span 的 `record_llm_usage()` 方法写入 trace。

### 5. `agent_usage.py` — Agent 批量用量捕获

`capture_response_usages()` 递归遍历 Agent 调用返回的复杂嵌套结构（dict、list、LangChain messages），提取所有 provider 响应的 token 用量。

```
response (Agent 返回的复杂对象)
    │
    ▼
visit() 递归遍历:
    ├── extract_llm_usage(value) → 找到用量 → 记录 + 停止深入
    ├── Mapping → 遍历 values
    ├── Sequence (非 str/bytes) → 遍历 items
    └── 有 messages 属性 → 遍历 messages
    │
    ▼
去重: 按 id() 跟踪已访问对象，避免循环引用
    │
    ▼
返回: [{model, prompt_tokens, ..., usage_source: "provider_response",
         usage_summary: {call: "agent_name[1]"}}, ...]
```

多个记录时自动编号 `[1]`、`[2]`，便于区分同一 Agent 调用中不同 LLM 调用的用量。

### 6. `node_instrumentation.py` — 节点装饰器

#### `@traced_node(event_type)` 装饰器

为 LangGraph 节点函数添加透明 span 采集，**不改变节点的业务行为**：

```python
@traced_node("planner")
def planner_node(state):
    # 业务逻辑，自动包裹在 span 中
    ...
```

**实现细节：**
```
wrapped(state, ...)
    │
    ├── _trace_recorder(state): 从 state["trace_id"] 获取 TraceRecorder
    │     └── 无 recorder → 直接执行原始节点（不做 tracing）
    │
    ├── recorder.span(event_type) 进入上下文
    │     失败 → 直接执行原始节点
    │
    ├── _current_span.set(span): 将当前 span 存入 ContextVar
    │     └── 节点内的 LLM 调用可通过 record_current_llm_usage() 自动关联
    │
    ├── 执行原始节点 node(state, ...)
    │     ├── 正常返回 → span_context.__exit__(None, None, None)
    │     └── 异常 → span_context.__exit__(error) → 重新抛出
    │
    └── _current_span.reset(token): 清理 ContextVar
```

**`record_current_llm_usage()`：** 从 `ContextVar` 读取当前 span，直接记录 LLM 用量——节点内部只需调用此函数，无需手动传递 span 引用。

### 7. `finalize_node.py` — 图结束节点

LangGraph 图的最后一个节点，负责汇总 trace、生成 evidence、写入本地 artifact。

#### 关键路径延迟计算

`_critical_path_latency_ms()` 基于 DAG 依赖关系计算：

```
execution_plan.steps = [
    {step_id: "step_1", dependencies: []},
    {step_id: "step_2", dependencies: ["step_1"]},
    {step_id: "step_3", dependencies: ["step_1"]},   ← 与 step_2 并行
    {step_id: "step_4", dependencies: ["step_2", "step_3"]},
]

for each step (拓扑顺序):
    cumulative[step_id] = max(dependency_latencies) + step_duration_ms

critical_path = max(cumulative.values())
```

---

#### `trace_finalize_node()` 完整流程

```
state (MetroAgentState)
    │
    ├── 1. 获取 TraceRecorder
    │
    ├── 2. active_registry.finish(trace_id, terminal_status)
    │       └── 等待所有 span 完成（或超时）
    │       └── 返回 finish_persisted (bool)
    │
    ├── 3. derive_trace_summary(state, recorder.final_summary)
    │       ├── status: terminal_status(state)
    │       ├── step_count / success_count / failed_count / degraded_count
    │       ├── e2e_latency_ms / critical_path_latency_ms
    │       └── total_tokens / estimated_cost
    │
    ├── 4. build_trace_evidence(state, evidence_snapshot, trace_id, summary, final_answer)
    │       输出: {schema_version, trace_id, final_answer_sha256,
    │              summary_binding, agent_path, plan, planning_events,
    │              tool_calls, spans, llm_usages, errors}
    │
    ├── 5. write_json → artifacts/traces/{trace_id}/summary.json
    │       内容: {trace_id, summary, final_answer, evidence, evidence_sha256}
    │
    ├── 6. 若 finish_persisted → update_span_artifact + update_final_summary
    │       失败 → summary["trace_degraded"] = True → 重写 artifact
    │
    └── 7. 返回 {"trace_summary": ..., "trace_artifact_uri": ...}
```

**降级策略：**
- 数据库写入失败 → `summary["trace_degraded"] = True`，但不影响本地 artifact 写入
- 本地 artifact 写入失败 → `trace_summary` 中仍保留 memory snapshot（recorder.final_summary）
- trace_finalize_node 本身抛异常 → 返回 `{"trace_summary": {"trace_error": ...}, "trace_artifact_uri": ""}`，**不中断图执行**

**Evidence 只保留评测所需最小证据：** agent_path、DAG（nodes + edges + agents）、planning_events（脱敏后）、tool_calls（只含 evaluation_arguments）、spans（只含 7 个关键字段）、llm_usages（只含 12 个字段）、errors。不保存密钥、完整用户问题或完整 chunk 文本。

### 8. `artifacts.py` — 原子文件写入

#### 安全路径解析

`_resolve_target()` 实现多层路径安全检查：

| 检查 | 拦截场景 |
|---|---|
| 空路径 / `.` | 写入根目录 |
| 绝对路径（POSIX 和 Windows） | `/etc/passwd`、`C:\...` |
| `..` 穿越 | `../../.env` |
| 符号链接 / Junction | 通过符号链接跳出 artifact_root |
| artifact_root 自身是符号链接 | 攻击者替换 root 指向 |

#### 原子写入

`_atomic_write()` 实现 **临时文件 + fsync + rename** 的原子写入模式：

```
1. 在目标目录创建 .filename.{random}.tmp 临时文件
2. 写入内容 → flush → os.fsync (确保落盘)
3. 再次校验目标路径安全性（防止 TOCTOU 竞态）
4. 校验临时文件父目录未改变
5. temp_path.replace(target) ← 原子重命名
6. finally: 清理残留临时文件
```

`ArtifactRef` 返回 `{uri (POSIX 相对路径), sha256}`，供调用方交叉校验。

#### 三种写入函数

| 函数 | 输入 | JSON 选项 |
|---|---|---|
| `write_json` | `Mapping \| list` → JSON | `ensure_ascii=False, allow_nan=False` |
| `write_jsonl` | `Iterable[Mapping]` → 每行 JSON | 同上 |
| `write_markdown` | 原始字符串 | 直接写入 |

### 9. `query_service.py` — 监控查询服务

只读、owner-scoped 的查询层，面向监控页面和 API。

#### DTO 层次

```
MonitoringFilter (输入) → TracePage / TraceDetail / MonitoringSummary (输出)
    │                          │
    ├── TraceListItem          ├── SpanDetail
    ├── TracePage              ├── LlmUsageDetail
    └── MonitoringSummary      ├── ToolCallDetail
                               ├── RagRetrievalDetail
                               └── TraceDetail
```

#### `list_traces()` — 分页列表

支持 6 种过滤条件：

| 过滤器 | 实现方式 |
|---|---|
| `user_id` | WHERE（强制，owner-scoped） |
| `started_after` / `started_before` | WHERE 时间范围 |
| `status` | WHERE 精确匹配 |
| `agent` | 子查询 `AgentSpan.trace_id WHERE agent = ?` |
| `model` | 子查询 `LlmUsage.trace_id WHERE model = ?` |

分页：`limit` 限制在 1–100；`offset` 最小为 0。

#### `get_trace()` — 详情查询

一次请求加载完整 trace：AgentTrace → AgentSpans（DAG 排序）→ LlmUsages → ToolCalls → RagRetrievals。

**Span DAG 排序（`_order_spans_for_display`）：** 拓扑排序，父 span 始终在子 span 之前，便于前端按层级渲染 trace 时间线。

#### `summary()` — 聚合统计

计算：总数、成功率、平均/P50/P95 延迟、总 token、总费用、工具调用数、工具失败率。

**百分位数计算**：`_percentile(values, 0.95)` 使用 `ceil(len * quantile) - 1` 作为索引，取上界而非线性插值。

### 10. `evaluation_service.py` — 评测持久化

提供两种评测结果写入方式：

| 方法 | 使用场景 | 是否写本地 artifact |
|---|---|---|
| `record_run()` | 评测运行器直接生成结果 | 是（同时写 manifest + case_results + summary + report） |
| `record_existing_run()` | 已有本地 artifact，只持久化 DB 元数据 | 否（artifact 已存在） |

**`record_existing_run()` 的幂等性：** 若 `run_id` 已存在于 DB → 直接返回已有记录，不重复插入。适用于评测 CLI 的 `--persist` 标志。

**`_normalize_case()` 的输入校验：**
- `case_id` 必须是非空字符串
- `metrics` 必须是 JSON 兼容的 Mapping
- `passed` 必须是 bool 或 None
- `reason` 截断到 512 字符

## 数据流与生命周期

### 一次 Agent 请求的完整 trace 生命周期

```
┌─────────────────────────────────────────────────────────────────┐
│ 1. 请求入口（API / agent_service）                                │
│    trace_id = uuid4()                                           │
│    registry.start(trace_id, {thread_id, user_id, round_id, ...})│
│    state["trace_id"] = trace_id                                 │
└─────────────────────────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────────────────────────┐
│ 2. 图执行                                                        │
│    @traced_node("planner") → span("planner")                    │
│        ├── LLM 调用 → record_current_llm_usage(response, ...)    │
│        └── span.set_result("success")                           │
│                                                                  │
│    @traced_node("agent", agent="knowledge_agent", step_id="s1") │
│    → span("agent", ...)                                          │
│        ├── LLM 调用 → span.record_llm_usage(...)                 │
│        ├── 工具调用 → span.record_tool_call(...)                 │
│        ├── RAG 检索 → span.record_rag_retrieval(...)             │
│        └── 异常 → span 自动 finish(status="failed")              │
│                                                                  │
│    @traced_node("aggregate") → span("aggregate")                 │
└─────────────────────────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────────────────────────┐
│ 3. trace_finalize_node(state)                                   │
│    registry.finish(trace_id, status)                            │
│        └── 等待所有 span 完成（最长 1s）                          │
│    derive_trace_summary(state, recorder.final_summary)           │
│    build_trace_evidence(...)                                     │
│    write_json → artifacts/traces/{trace_id}/summary.json        │
│        └── 原子写入 + SHA256                                     │
│    若 DB 持久化成功 → update_span_artifact + update_final_summary│
│    若 DB 持久化失败 → summary["trace_degraded"] = True           │
└─────────────────────────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────────────────────────┐
│ 4. 后续消费                                                      │
│    query_service.get_trace(trace_id, user_id) → 监控页面         │
│    run_deepeval.py → 读取 trace evidence → 评测                  │
└─────────────────────────────────────────────────────────────────┘
```

## 异常处理设计原则

**核心原则：可观测模块不能因为自身失败中断用户请求的正常回答。**

| 层级 | 策略 | 实现 |
|---|---|---|
| Store 初始化 | 失败 → 透明降级为 `_UnavailableTraceStore` | `TraceRegistry.start()` |
| `@traced_node` | 任何异常 → 直接执行原始节点 | try/except 包裹 span 创建和执行 |
| `_call_store()` | 存储失败 → 捕获异常、记录 error、返回 False | store 方法不抛异常 |
| `trace_finalize_node` | 异常 → 返回 `{"trace_error": ...}`，不抛 | 最外层 try/except |
| `extract_llm_usage()` | 任何解析失败 → 返回 None | 最外层 try/except |
| `SqlAlchemyTraceStore._write()` | 写入失败 → rollback + close，返回 False | 不向上传播 |

## 测试策略

| 测试类型 | 方法 | 验证目标 |
|---|---|---|
| **TraceEvent 生命周期** | 创建 → finish → 验证 duration_ms 和 attributes 合并 | start/finish 正确 |

| **@traced_node 透明性** | 装饰一个会抛异常的节点，验证异常正常传播且 span 记录为 failed | 不改变节点行为 |
| **TraceRecorder finish 协调** | 在 span 内调用 finish，验证等待超时和 unfinished_span_count | 关闭协调正确 |
| **Store 降级** | Mock SQLAlchemy 初始化失败，验证降级为 `_UnavailableTraceStore` | 降级路径 |
| **`extract_llm_usage()`** | 传入 OpenAI / DeepSeek / Qwen 各 provider 的响应 | 多 provider 归一化 |

| **Evidence 签名** | 篡改 evidence 后验证 `trace_evidence_digest()` 不一致 | SHA256 绑定 |

## 维护建议

1. **新增 Agent 节点、工具或 LLM 调用时，同步考虑 trace 字段**：agent_path（节点级 agent 名）、event_type（span 类别）、tool_name 和 arguments_summary（工具调用）、model 和 token（LLM 调用）。

2. **不要绕过 `TraceStore` 协议直接操作 ORM 模型**：所有持久化通过 `TraceRecorder` → `TraceStore` 接口，保证未来切换存储（如从 SQLAlchemy 换到其他）只需新增一个 `TraceStore` 实现。

3. **`llm_usage.py` 的字段映射表是活的**：当新 provider 使用不同的 token 字段名时，在 `_PROMPT_TOKEN_KEYS` 等元组中追加即可，无需修改提取逻辑。

4. **在线评测监控页面应优先通过 `query_service.py` 或 `evaluation_service.py` 读取聚合数据**，不直接扫描本地 trace 文件。这样后续替换存储或加权限控制更稳。

5. **`artifacts.py` 的原子写入保证了半写入文件不会被读到**，但调用方仍需在读取时校验 SHA256（如 `run_deepeval.py` 的 evidence 校验链）以防御存储层面的篡改。

6. **`trace_finalize_node` 的 `finish_wait_timeout_seconds` 默认 1 秒**：若生产环境出现大量 `trace_close_timeout`，说明有长时间运行的 span 未正确关闭，应排查对应节点的 span 生命周期管理。

7. **不要往 `attributes` 中放秘密**：`TraceEvent.attributes` 经过 JSON 序列化后存入数据库和本地文件，日志中也可能出现。
